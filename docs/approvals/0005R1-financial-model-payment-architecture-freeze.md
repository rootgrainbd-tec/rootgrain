# ROOTGRAIN — 0005R1 FINAL FINANCIAL ARCHITECTURE FREEZE

**Document:** docs/approvals/0005R1-financial-model-payment-architecture-freeze.md  
**Status:** AWAITING APPROVAL  

## 1. ADVANCE SEMANTICS
The architecture explicitly separates the following semantics:
- **Suggested Advance:** A UI-only calculated value (20% of Total) to prompt the user. Not stored in the database.
- **Advance Required:** A newly proposed field `Order.advanceRequired` representing the negotiated amount required before processing begins.
- **Payment Received:** An individual financial receipt recorded in the ledger (`PaymentRecord`).
- **Total Paid:** The sum of all valid payments.
- **Balance Due:** Derived exclusively as `Grand Total - Total Paid`.

## 2. PAYMENT RECORD IS SOURCE OF TRUTH
`PaymentRecord[]` is established as the absolute financial source of truth for all post-upgrade payments.
The legacy field `advancePaid` will be functionally retained as a **cached aggregate** for `Total Paid` to ensure backward compatibility for old orders. 
- **Legacy Behavior:** If an order has `advancePaid > 0` but no `PaymentRecord` entries, `advancePaid` remains the source of truth. 
- **New Behavior:** When a `PaymentRecord` is created, it transactionally updates `advancePaid` (as `Total Paid`) and `balanceDue`. No historical `PaymentRecord` events will be fabricated.

## 3. ADVANCE REQUIRED
**Proposed:** `Order.advanceRequired` (Type: `Int?`, Nullable). 
This field allows Admins to record a specifically negotiated advance. It remains editable by Admins if renegotiation occurs prior to confirmation.

## 4. PAYMENT RECORD PROVENANCE
The `PaymentRecord` model requires the following fields to ensure complete provenance:
- `orderId` (Which order)
- `amount` (How much)
- `type` (What: e.g., ADVANCE, SETTLEMENT)
- `method` (How: BKASH, CASH, BANK, OTHER)
- `reference` (Reference ID)
- `status` (COMPLETED)
- `paidAt` (When)
- `recordedById` (Who: Admin User ID)
- `idempotencyKey` (Duplicate prevention)

## 5. GENERIC REFERENCE
The strict `@unique` constraint on the existing `bkashTrxId` prevents generic references (like "Cash Receipt" or offline bank references that might duplicate). 
**Strategy:** Replace `bkashTrxId` with `reference String?`. 
Uniqueness validation for digital transaction IDs (like bKash) will be enforced at the application layer, allowing manual/cash payments to use non-unique or empty references.

## 6. IDEMPOTENCY
Payment creation must be idempotent.
**Strategy:** Implement `idempotencyKey String @unique` on `PaymentRecord`.
- Generated by the client (UUID) when the Admin clicks "Save Payment".
- Persisted alongside the payment.
- If a network retry occurs, the database will safely reject the duplicate key, preventing double-booking.

## 7. CONCURRENCY SAFETY
To survive read-modify-write race conditions (e.g., two Admins recording a ৳7,000 payment simultaneously), the following atomic sequence is required:
1. `prisma.$transaction(async (tx) => { ... })`
2. `tx.order.findUnique({ ... })`
3. Validate payment amount against `balanceDue`.
4. Create `PaymentRecord` (idempotency key enforces uniqueness).
5. Aggregate `tx.paymentRecord.aggregate({ _sum: { amount: true } })`.
6. Update `tx.order.update({ data: { advancePaid: newSum, balanceDue: total - newSum } })`.

## 8. TRANSACTIONAL FINANCIAL INTEGRITY
The `PaymentRecord` creation and the cached `advancePaid`/`balanceDue` updates must execute entirely within the single Prisma `$transaction` defined above. Rollback semantics are native to Prisma: if any query fails, the entire block reverts, guaranteeing no orphaned payments or desynchronized balances.

## 9. PAYMENT VALIDATION
The following invariants will be enforced in the transaction:
- `Payment Amount > 0`
- `Payment Amount <= Remaining Balance`
- `Total Paid >= 0`
- `Total Paid <= Grand Total`
- `Balance Due >= 0`
- `Balance Due = Grand Total - Total Paid`

## 10. NO NEGATIVE PAYMENT REFUNDS
Refunds are explicitly out of scope. `PaymentRecord.amount` must be positive. If refunds are needed in the future, a dedicated `RefundRecord` model will be proposed.

## 11. PAYMENT VS ORDER STATUS
Order Status (`PENDING`, `CONFIRMED`, `PROCESSING`) and Payment State are strictly decoupled. 
- Order Status manages logistical progression.
- Payment State (Total Paid, Balance Due) manages financial obligations.
An order can technically be confirmed without full payment if business logic or an Admin dictates it.

## 12. PAYMENT RECORDING VS STATUS UPDATE
The backend will expose two distinct operations:
- `recordPayment()`
- `updateOrderStatus()`
Even if the UI couples them in a single workflow, the backend will treat financial recording and logistical status mutation as independent operations.

## 13. CANCELLATION / REJECTION
If an order is marked `CANCELLED` or `REJECTED`, the `PaymentRecord` history remains completely untouched. Financial facts are immutable, preserving the payment history for future manual refunds.

## 14. ORDER FINANCIAL IMMUTABILITY
`Order.subtotal`, `Order.discountAmount`, `Order.shippingCost`, and `Order.total` are functionally immutable after creation. Existing code does not expose mutation endpoints for these fields, and this strict immutability will be preserved.

## 15. PROMO SNAPSHOT
Promotional discounts will continue to be safely snapshotted as `discountAmount` upon checkout. Changes to promo configurations will never retroactively modify historical financial snapshots.

## 16. DELIVERY SNAPSHOT
Delivery costs will continue to be safely snapshotted as `shippingCost`. Future delivery matrix updates will not alter historical orders.

## 17. TOTAL PAID
The legacy `advancePaid` field on the `Order` model will be retained as a **Total Paid cache**. It will be strictly synchronized within the payment creation `$transaction`.

## 18. BALANCE DUE
`balanceDue` will be retained as a **cached + server-side invariant** field. It provides fast read access for the Admin dashboard while remaining strictly synchronized with `Total Paid` within the transaction block.

## 19. HISTORICAL ORDERS
No synthetic `PaymentRecord` events will be generated for old orders. 
Old orders will retain their legacy financial snapshot inside `advancePaid`. If an old order receives a *new* payment post-upgrade, the transaction will sum the new `PaymentRecord` and carefully add it to any untracked legacy balance if necessary, though ideally new payments are only for new orders. 

## 20. PAYMENT RECEIPT
A Payment Receipt document will represent a specific transaction event, rendering the `PaymentRecord` alongside the immutable order snapshot. It will NOT dynamically recalculate if subsequent payments are made.

## 21. DOCUMENT ARCHITECTURE
Financial documents (Order Confirmation, Payment Receipt) are explicitly separated from Operational communications (Processing, Dispatch, Cancelled notifications).

## 22. EXISTING PDF SYSTEM IS PROTECTED
The existing `pdfGenerator.ts` architecture utilizing `pdfkit` (with font externalization) remains protected. It will be extended to support Payment Receipt templates, eliminating the need for a secondary PDF engine.

## 23. PDF FAILURE ISOLATION
If `generateInvoicePDF` fails, the financial database transaction MUST remain successful. The failure will be logged, and the standard HTML email will still dispatch, avoiding false negative financial rollbacks.

## 24. PAYMENT / EMAIL DECOUPLING
If the `Resend` email dispatch fails, the `PaymentRecord` must remain successfully committed to the database. Emails are asynchronous side-effects.

## 25. PAYMENT / DOCUMENT DECOUPLING
If an Admin clicks "Retry Receipt", the system will only regenerate and email the document. It will NOT duplicate the financial `PaymentRecord`.

## 26. ADMIN AUTHORIZATION
All financial mutations and status changes are strictly protected by `requireAdmin()` in Next.js Server Actions.

## 27. PAYMENT METHODS
The `PaymentMethod` enum will be expanded to support:
- `MANUAL_BKASH`
- `BANK_TRANSFER`
- `COD`
- `CASH` (NEW)
- `OTHER` (NEW)

## 28. PAYMENT STATES
The `PaymentStatus` enum (`INITIATED`, `COMPLETED`, `FAILED`, `REFUNDED`) is preserved. Manually recorded Admin payments will default to `COMPLETED`.

## 29. DATABASE MIGRATION STRATEGY
- **Order Model**: Add `advanceRequired Int?`. No existing rows affected.
- **PaymentRecord Model**: 
  - Add `reference String?`.
  - Add `recordedById String?`.
  - Add `idempotencyKey String @unique`.
  - Remove `@unique` from `bkashTrxId` (deprecating it in favor of `reference`).
- **PaymentMethod Enum**: Add `CASH`, `OTHER`.

## 30. LEGACY COMPATIBILITY
Old orders remain fully readable. Admin details, tracking, and existing invoices will continue functioning by reading the cached `advancePaid` aggregate where `PaymentRecord` arrays are empty.
